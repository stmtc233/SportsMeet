# 写作:界面文案与提交信息

## 为什么有这条

AI 写文案时习惯把自己的推理过程原样搬进去:实现条件、因果链、适用范围、好处、撤销方法塞进一句话,用户读不完也读不懂;提交信息则把整份改动说明塞进标题行,`git log --oneline` 一条就是一屏。两者的读者都只花几秒,要给的是结论,不是推导。

## 界面文案

适用于应用界面、打印模板(秩序册、成绩册等)里的固定文字,以及 service 返回给用户看的错误提示。日志、代码注释、细则文档、MCP 工具说明不受本节字数限制。

### 默认不写

任何界面上要加一行字(副标题、提示、说明、状态行等),先问:删掉它,用户还能操作、看懂状态吗?能就不写。操作提示、状态回显、功能介绍都属于这类,交互和状态由控件本身表达。

### 写什么

- **只写用户要知道的结果与下一步**:会怎样、该做什么。为什么会这样(按指纹比对、在事务里重算)是实现,不进文案。
- **不写条件分支树**:「A 不行就靠 B,B 不行再 C」只留用户当下面对的那个结果;用户不用操作的自动回退不写。
- **不复述**:副标题不重复标题;下方控件已显示的值不写进副标题;没有标题之外的新信息就不写副标题。
- **只用界面上的名字**:引用按钮、页面、设置项用界面原名加「」;同一操作全应用一个叫法。代码概念(`heat`、`slot`、`previewHash`、`keepReason`)不进文案。
- **不写口语和卖点**:不用「就」「一下」「其实」「哦」「啦」「~」,不写「…，就…；…」式逗号长链,一句只说一件事。好处只在它是用户决定开关的依据时写,压到几个字。
- **失败与警告**:先说后果,再说动作;不道歉,不解释内部原因。

### 标点与用词

- **中文文案用全角标点**:`，。；：？！（）`,引号与按钮名用「」。全角标点前后不加空格(`Ctrl+S（Mac 为 ⌘+S）`)。
- **保留半角的地方**:数字、时间与成绩(`1,000`、`12.34`、`1:05.67`、`6.52m`)、文件名与路径、快捷键提示、CSV 表头与导入格式示例(`王五,1002`)这类数据,以及日志、异常消息、MCP 工具说明(给 AI 读,不是界面)。
- **术语统一**:按 [AGENTS.md](../../AGENTS.md) §2。「组」不叫「组次」;「报名」不叫「参赛登记」;「编排」指把报名者排进组和位置,不用来指整个系统。

### 长度

按汉字计,变量取典型展开值:

| 位置 | 上限 |
|---|---|
| 标题、按钮、开关名、分段选项 | 12 字;按钮用动词短语(「自动编排」) |
| 列表行 / 开关副标题 | 一行,20 字 |
| 对话框正文 | 2 句、60 字;风险确认类最多 3 句。并列的多项事实换行分条 |
| 状态条、提示条、Toast | 15 字 |

超出上限先删实现细节和重复信息;删完仍放不下,说明内容该放进帮助文档,而不是副标题或弹窗。

### 示例

开关「同单位分散」的副标题:

```
改前:开启后自动编排时会尽量把同一参赛单位的运动员分到不同的组，如果人数太多无法完全分开，就按人数均衡分配
改后:同单位尽量不同组
```

改前复述了开关名,写了算法的回退分支。用户只需知道开了会怎样。

删除项目的确认对话框:

```
改前:删除项目会同时删除该项目下的所有轮次、组、位置和已录入的成绩，以及所有报名记录，此操作无法撤销，请谨慎操作。
改后:将删除 3 组与 24 条成绩，无法撤销。
```

改前把级联删除的实现列了一遍,还用了套话。给出数量,用户能直接判断代价。

## 回复用户

回复用户一律用中文(用户要求):说明、总结、提问都写中文;代码标识符、文件路径、命令、提交哈希保留原样。

## 提交信息

用户没确认就不提交(用户要求):改动完成后留在工作区,说明改了什么并询问是否提交,不要改完顺手提交;用户明确说提交(或本次请求里就要求提交)才提交。合并、改写已有提交同样要用户确认。确认后没说分支就提交到 `main`,没说推送就不推送。回复用户时正常说明即可,不提按哪份文档 / 什么格式写的。

### 格式

```
type(scope): 摘要

- 正文第一条
- ……
- 同步更新 AGENTS.md、arrange.md
```

- **标题**:`type` 取 `feat` / `fix` / `refactor` / `perf` / `docs` / `test` / `build` / `chore`,`scope` 取模块名(`arrange`、`scoring`、`interchange`、`report`、`mcp`、`store`、`ui`、`design`…)。摘要 ≤ 30 字,写用户可见的变化或修掉的现象;不写实现手段、类名、常量值,不带句号。一个标题装不下两件事,就拆成两个提交。
- **正文**:空一行后 3–8 条,每条一句,只写 diff 里看不出来的:为什么这样做、关键取舍与边界、已知限制、验证情况(单测 / 在哪个系统上手动验证;没验证就写没验证)。
- **不复述 diff**:不罗列改了哪些类、函数、文件、常量;只有读者必须知道的入口(新的公共入口、数据迁移)才点名。bug 修复写一条「原因:…」,不写「原先…实测…」式叙事。
- **文档同步**写在正文最后一条:「同步更新 AGENTS.md、xxx.md」。
- 多行信息用 heredoc 交给 `git commit -F -`,不要把全部内容塞进一个 `-m`。

### 示例

```
feat(arrange): 自动编排支持同单位分散

- 编排页「自动编排」新增开关,默认开
- 只排未分组的报名者、只追加新组,已有组不动
- 人数放不下时按组人数均衡,不报错
- 补单测;macOS 手动验证 120 人分 15 组
- 同步更新 arrange.md
```

bug 修复:

```
fix(scoring): 并列成绩名次跳号

- 原因:并列后下一名按位置序号计,应按并列人数顺延
- 两人并列第 2 时下一名为第 4
- 补单测覆盖径赛与远度
- 同步更新 domain.md
```
